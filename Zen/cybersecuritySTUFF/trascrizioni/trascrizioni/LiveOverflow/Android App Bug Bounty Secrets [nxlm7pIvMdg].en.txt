Anyway, You probably ask yourself “I don’t understand, what is the vulnerability here”. And I’m glad you asked, so let me explain what he actually found here. We need to explain three concepts. Android Intents Content Providers And Android permissions 1. Android Intents. In the android ecosystem you have the concept of Intents. Intent is a weird word to you, maybe? So try to not get confused by new terminology. It’s very basic when I replace the word “intent” with the word “data”.. Android apps can send and receive data. So one app can send data to another. For example when you want to share a website. You open up this share view and you can click on another app. For example Message. This then opens the message app and it has the link I wanted to share. Under the hood, the browser app sent this data, so an “intent”, to the message app with the data, the URL. That is a very basic example and of course you can send a lot more than just text. Intents have a ton of features. You will see in just a moment. But for now, intents are simply used to pass data to other apps. As you can see, Intents are a very typical attack surface for android apps. A malicious app could send any kind of intents to other apps. And if the app handles the intent badly, it could lead to all kinds of security issues. 2. Content Providers Another important android feature and threat surface to understand here is, the concept of ContentProviders. Apps can define content providers and it does what the name says. Provide content. They try to abstract away how data is really stored. Content providers work through “URIs”. So if you have your notes stored in a SQL database, you could create a content provider to access notes instead. Then no SQL queries are needed and you can just use a URI like this. So now that your app stores notes and has a content provider for them, your app could expose this content provider to allow other apps to access those notes. But of course it’s a bad idea to just have the content provider publicly accessible. It would be much better if another app has to request access, and then the user has to confirm this first. This can be implemented again with Intents. An external app could ask your app, can I get access to the notes, you display a dialog to the user and if the user hits okay, you send back an intent with the flag, FLAG_GRANT_READ_URI_PERMISSION. Adding this flag to the intent you send back to the requesting app grants the other app to access the content via the notes URL. So you shared the content provider with another app. 3. Android Permissions And now one last concept we need to understand, android permissions. In this case the snapseed app has read and write permission to external storage. And by requesting these permissions, the app will actually has access to the “hidden” or rather “internal” content provider for files on the external storage. The URL for that looks for example like this content://media/external/video/media. That’s it. Snapseed can now use this content provider to access files on the external storage. Also it’s important to note, that our attacker app does not have these permissions. It cannot access the file storage. Okay. Now we have all three concepts we need. And we can come back to the vulnerability Sergey found. In the meantime he has written up his malicious attack app, so let’s checkout his code. When the malicious app starts, he creates a new Intent object. And sets various values. But ignore these for now, important is only the setClassName and this putExtra. With setClassName you can specify exactly the receiver of the intent. In this case it’s the snapseed app bundle as well as the vulnerable activity class. When he now starts this activity, he sends this intent, it will launch the main activity from snapseed with this extra stream data. Now let’s go to the receiving side. Here the MainActivity now tries to access this STREAM data and CAST it to an android.net.Uri. But the intent did not contain a URI. it’s this wow string. So this triggers the required ClassCastException! which causes this alert dialog to be created. So now that the app has the dialog, there is this OK button to confirm you read the error. And we know what this button does from the onClickHander. It returns a result back to the app with. setResult. it sets the result value to 0, probably to tell the other app that it didn’t work. 0. false. Fail. But additionally it also adds the original intent that was sent to the app from sergey. Probably to give the receiving app a bit of context, what was the intent that didn’t work. But this is dangerous. We know how android passes data between apps. So of course this result is sent back as an intent to the malicious app. And now think about how the intent looks like that it sends here. It’s the intent that sergey created, and now the other fields become important. This intent contains the EXTERNAL_CONTENT_URI, as well as the flag FLAG_GRANT_READ_URI_PERMISSION. Do you see where this is going? By snapseed sending such an intent to the malicious app, it tells the android operating system, “snapseed would like to give the attacker app the permission to access my internal file content provider”. Which means, the malicious app has now the permission to use the snapseeds content provider for external files. here in the result handler, so where the attacker app receives the intent, in there Sergey can now access the media storage. let’s run the full exploit.
