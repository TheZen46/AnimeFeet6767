Report a security issue to a bug bounty program, and get money. Repeat that, and you get rich. But is it really that easy? Well… the problem is you have to find vulnerabilities. You cannot report the same issue over and over and hope to get money, right? Right? In this video I want to talk about a few “unfixable bugs”, or “unfixable issues”. And how they can maybe?, be used to generate an endless stream of money. &lt;intro&gt; Have a look at this bug bounty report. “Possible denial of service when entering a loooong password”. And the issue is quite simple. Go to the signup page, enter a looooong password. Aaaand “This may lead to the website becoming unavailable or unresponsive.”. The argument here is that hashing a large amount of data will take a lot of server resources. Result is a denial of service. So of course, you get 100$ bounty and even a CVE for it. Luckily for us, nextcloud is open source, so we can see the actual fix. In the PasswordController.php they now check the maximum length of the password to be 100. But… I’m a little bit suspicious here. In the nextcloud documentation about password hashing, we can see that it uses Argon2, but you can also configure it to use phps PASSWORD_DEFAULT. This tells me that it simply uses PHPs password-hash() function. See here, there are options, PASSWORD_DEFAULT, PASSWORD_BCRYPT, or as the documentation indicated, PASSWORD_ARGON2I. Now fun fact, if you use the default bcrypt, which is also not too bad, then “the password parameter is being truncated to a maximum length of 72 bytes.”. So with that configuration, there wouldn’t be an issue. But… is it maybe an issue for ARGON? Well? Let’s throw up a quick experiment. Here is a loop, we generate some random password with increasing length $i. And then we measure the time before and after the hashing to see how long it took. That’s a good indication for how many resources it’s eating up. And we can see now that it always takes roughly 0.3s. But the report was about 10.000 characters long password. We are slowly getting there… mhhh… still 0.31s. Let’s wait a bit longer. UH, we start to see a few 0.32s. But we are now in the millions. So like a megabyte long password. But now we finally see the time increasing more! But… PHP Fatal error. This didn’t crash because of the hash. We generated a way too long password string here. The last one was 51 million characters long. Long story short. I don’t believe “password hashing process will result in CPU and memory exhaustion”. So as this comment by kotori on twitter said it nicely in response to my question, “I guess you will most probably hit maximum upload size limit first…”. But who cares, if you get a bounty, and a CVE, keep reporting it. Here is nextcloud again, just a different endpoint. This time in the LostController, so forget password functionality. No bounty paid yet, but it should get one. And this also got a CVE again. Another report from imgur “the server might not be able to handle such lengthy passwords coming from different machines simultaneously”, you get a 250$ bounty for that. So is this vulnerability an infinite money glitch? Just keep reporting this, claim that it’s an issue and get bounty and CVEs? Luckily submitting this is not always successful. GitLab for example pushed back against the reporter who kept insisting that this is a vulnerability. Referencing other reports that were deemed valid. But in the end not only was the report false, but GitLab already had password length restrictions. So are these resorts all fake? no… I have to admit, the issue is not always this blatantly false. For example in the web framework Django in 2013, there maybe was a valid issue. Django implemented pbkdf2 by hand. I took this code and cooked up another small test. So we again generate increasingly longer passwords, and hash them with this function. And you can see, it does take significantly more and more time. The security advisory stated: “A password one megabyte in size, for example, will require roughly one minute of computation”. In 2023 this is not true anymore, a password of 1 megabyte on my laptop is under 10 seconds. But still, it scales. Send 20 megabytes and you are probably at the 1 minute mark. But I have more to complain about here. You see, okay the code might hang the process for a while. BUT the attacker also has to send MEGABYTES of data, you cannot send this very fast. And so this DoS attack takes time and takes up resources on the attacker side as well. Which leaves us with a big question, at what resource ratio does a denial of service become an issue or not. It’s clear that an extreme example like a single request killing the complete server is bad. But there is a lot in between. Where do we draw the line? Is sending megabytes of data not already, you know, asking a lot from the attacker? That’s debatable, and that leads us to the next argument. The impact of a denial of service and generally “resource exhaustions” also depends on how the web application is deployed. Actually most production server setups have timeouts. For example in PHP there is max_execution_time, of 30s. And nginx has I believe 60s by default. Which means even if the password would theoretically take 10 minutes to compute, the server already kills the process after 30seconds. Now we can argue over these default numbers. Maybe 30 seconds is too long. But there is a reason why it's set to these numbers. Apparently we kinda accept that some requests might take longer. But maybe we also say it is still an issue, a couple of these hanging requests could maybe stop the server from being able to answer to regular users. BUT on more modern serverless deployments, maybe they automatically just keep spinning up virtual machines to handle more users. And that probably solves the availability issue. At a cost though, maybe these VMs become expensive? But now ask yourself. Is it more expensive to spin up a few machines when the attacker doesn’t even know how much it will cost the business, versus spending hundreds of dollars on bounties, and the hourly rate of an engineer triaging reports, writing security advisories and implementing “fixes”? So if the argument for these denial of service issues becomes that a denial of service is costing the business for example lost revenue, then you have to balance that with the cost of the supposed fixes. Generally we would say, “fix is always better”, because then it’s fixed. Problem solved for eternity, right? But what if I told you. you cannot “fix” this issue? That’s basically the gist of this whole video. These are “Unfixable” bugs. It’s a game of whackamole. I show you. For example here is another nextcloud report about “Denial of Service by requesting reset password”. This person apparently sent over 1000 requests to the password reset endpoint, which made the server not responsive for over 1 hour. Sounds bad. So the reporter got 250$ in bug bounty reward and a CVE on top of it. But to me my tingly feelers were telling me something is off here. That sounds weird. So I looked into the source code of the fix to learn about what the original code did. Nextcloud implements a BruteForceMiddleware which “performs the bruteforce protection”. And if an endpoint is marked with “BruteForceProtection”, then the throttler-&gt;sleepDelay() function was called. The fix to this issue is calling throttler-&gt;sleepDelayOrThrowOnMax instead. But let’s think about the original code first. Do you get a sense where this is going? Well… sleepDelay() calls getDelay() with the user’s IP. So if one IP keeps sending more and more requests, the delay will increase. The server process literally sleeps for many seconds. No clue how large the delay can grow, but that could easily go up to minutes, maybe an hour. this code was added in 2016 for security to implement brute force protection. And now a hunter 4 years later in 2020 tries to bruteforce the password reset endpoint. Does it click? Because the attacker sends the requests from the same IP, these requests start to sleep(). And now think about what the bug hunter wrote “the server was not responsive for over 1h”. They triggered the sleep with their own IP and couldn’t reach nextcloud again. So was this bug bonty report completely bs? Well actually, probably it was a real denial of service, because request throttling, when implemented like, is inherently flawed. If an attacker attempts to bruteforce, the server will sleep, and regular requests by users can still be handled. BUT, if the attacker does too many bruteforce attempts, then maybe too many backend instances sleep, and regular users can not be responded to anymore. That’s a dos. But it is a working “fix” against bruteforce. You cannot bruteforce because the server is sleeping. But the server is sleeping, now you have a DoS issue. And so let’s have a look at the fix of this bug report, we see the code was changed from sleepDelay() to sleepDelayOrThrowOnMax(). This code now gets a max amount of allowed requests for the IP, and if that is reached it doesn’t sleep anymore, but immediately throws a 429 Too Many Request error. So okay, the bug report was valid? And the issue is fixed? Well… in my opinion not really. Because there is no real fix. It’s always a game of whackamole. It’s unfixable. So listen now, because you now get a chance to submit the issue again, get a bounty and a CVE. Okay… listen. It all started apparently with a bruteforce issue on the login. There were no bruteforce protection against bruteforcing, so they implemented request throttling. This however caused a denial of service due to it being implemented with sleeps(). We get another report and now we limit how much the throttling can sleep, and also how many requests per IP can trigger it. So the solution seems to be IP rate-limit. Is that the answer to everything? It seems so when you look at reports. 100$ for login bruteforce, “fixed” with IP rate-limits. Here a report without a reward, but still valid and the fix implements rate-limiting with IP address. But, IP rate-limiting can always be bypassed, with more IPs. There are attackers out there that can just send lots of requests through TOR, use public proxies, use VPNs. Or an evil attacker simply has a botnet. There are so many ways you can bypass this. Which means, you could still cause this denial of service, or even perform the original bruteforce issue. Here for example a twitter bug report getting 420$ for bypassing the IP rate limit, by using different IPs. Remember the weblate fix from before, where they fixed bruteforcing with IP rate limit. The fix is from the 27. April. Literally on the day of that fix, another user, “Shame upon him who thinks evil upon it”, reports that you can bypass this with more servers, or more IPs. So you should actually implement rate-limits per user account. So yeah, you heard it here… I think we could now report a DoS issue to nextcloud, arguing that you can simply use more IPs. But I refuse to report that, I think that’s a dirty game. Because honestly, how would they fix that issue? okay, well, request throttling with sleeps is inherently flawed due to the denial of service. So yeah, that’s a valid report I guess. BUT the reason they implement it like this is for anti bruteforce. Removing the throttling allows bruteforcing again. Prevent the bruteforce with IP rate-limits again? Well, if an attacker really wants, they can always get more IPs and bypass this. So the complex reality is that yes, request throttling with sleep is maybe causing the whole server to become unavailable. But at least that definetly protects against bruteforce. Server down, no bruteforce. And depending on your threat model, maybe that’s exacgly what you want. Okay, maybe we implement other ways of rate-limits then. We talked about bruteforce, right? Maybe we want to make sure somebody cannot bruteforce the password of a user? If IP rate-limiting is not perfect, maybe we just rate-limit logins per user? Instacart appears to do the same. On mobile the user didn’t get locked out, but the fix was to lock the account. And the customer then gets an email to unlock the account again. Is this finally the end of the chain, did we finally reach the correct way to fix this issue? Well if we look into OWASP about Blocking Brute Force attempts, specifically combating it with account lockouts, they write. “An attacker can cause a denial of service (DoS) by locking out large numbers of accounts.”, “An attacker can cause a diversion by locking out many accounts and flooding the help desk with support calls.”. And so now we come into the realm of threat modeling, and different users and different usecases have different requirements. Maybe YOU prefer your nextcloud server to be locked up when being attacked, to stop any bruteforce attempts. While somebody else doesn’t care about the bruteforce because they use secure passwords and rather have the server just not do any throttling at all. It’s unfixable. There are always arguments and edge cases and different requirements. But let’s say we like locking out users, that fits our threat model. The problems just keeps going. From the instacart report for example we know that they send out an email for users to unlock their account if it got locked due to brutefforce attempts. So we could now abuse that and trigger sending lots and lots of emails. Sending emails could cost money, but worse, it could result in the email being marked as a spam by some systems, due to the flood of them. Which could really negatively impact the business. Essentially blocking many legitimate users from receiving important emails, for example when they try to signup or after they purchases something. And suddenly we realize, we are right at the beginning, back at triggering some kind of denial of service against the system. And we now try to fix that. Request throttling? Ip-Rate limits? Take your favorite poison. And once the drugs hit your brain, realize that it’s even worse than you imagined. We just talked about issues surrounding logins. But those are not the only endpoints that exist. Every website, especially a lot more complex website, probably have some HTTP API that is “expensive” to execute. Maybe an image upload, upload gigabytes of data without rate-limits, filling up their cloud storage and triggering massive costs. Also many services generate thumbnails or crop images on uploads, that’s all computing power. Maybe not much, but without rate-limit on those endpoints, and maybe a little bit larger images, still causing some resource exhaustion. Any kind of “data import functionality” usually is vulnerable to denial of service attempts. That’s just computationally expensive. Or maybe it’s even expecting a .zip file. And you can throw in a zipbomb. You didn’t find a site with such features? How about submitting a very very long comment with 50.000 characters on GitLab. Apparently that triggered some processing on the server resulting in 1000$ bounty and a CVE-2019-15593. I can almost guarantee you, you can find DOS issues basically anywhere and everywhere. And they go hand in hand with “lack of rate-limit” and no bruteforce protections, because there simply does not exist a clear “fix”. You cannot really “fix” these issues. In my personal made up intuitive definition of what is a “vulnerability”, a vulnerability has to have some kind of clear fix. SQL injection, fix the SQL injection. CSRF, add a CSRF token. IDOR, add proper authorization. This is not the case for most DoS or rate-limit issues. Small footnote here. Of course there are also other DoS issues. Like complete server crashes that don't recover. Or a 6 digit verification code which can be easily bruteforced. But the solution there is usually not rate-limit, but math. The code has to be longer, or include letters to become probabilistically impossible to guess. But generally, these DoS and rate-limit issues are unfixable. You can always argue and find edgecases where it becomes weak again. This is especially true for self-hosted service like nextcloud. Everybody has different threat models. If you deploy that on a shared raspberry pi 1, if it even runs on there, then of course a dos is much easier and might happen with 5 regular HTTP requests. But when it’s deployed on a large server, maybe with sensible request timeouts and being able to dynamically spin up more nodes, even the most expensive request is handled like “whatever”. So I hope I made it clear why I think for these issues there is no “one fix for all”. It always comes down to very unique situations and threat models. And now if you look around in the “cybersecurity” industry, DOS is not the only issue of that kind. There are many more. For example “insecure browser password storage”. Because somebody wrote a script, or malware, to steal the passwords. It looks bad on first sight, but when you spend 1 minute thinking about it you should realize it makes no sense. Of course malware can access the passwords. Even when a company like kaspersky aggressively markets their own password manager to be so much more secure than the browser password stores, it’s trivial to write a malware to steal the passwords out of any password manager once it’s unlocked as well. Another good example is software obfuscation and anti-reversing. The game industry has tried for decades to solve the problem of piracy. And yet every game still got cracked. And now we have smartphones, and developers desperately want to obfuscate and prevent reversing of their apps. With enough dedication and efforts, it can always be reverse engineered. It’s a game of whackamole. It’s an endless circle. And endless circle of moneyyy. Maybe you have heard this from security people before. “If we do our job right, we are not needed anymore”. That is true - if we could solve and fix all the security issues, then there are no security issues left. Our profession is not needed anymore. The problem is though, companies, and maybe we security consultants and bug hunters as well, we slip right into those cracks. Companies selling android obfuscation services. Security scanners reporting on CVEs in NodejS libraries that have 0 impact on the actual web application. Password managers fear mongering against stored passwords in the browser, suffering from almost the same threat model. Security Consultants reporting Account enumerations on login forms, while there are a dozen more endpoints that leak whether a user exists or not. Or recently, credential stuffing! If hacking with real vulnerabilities becomes too hard and even “black hats” cannot compromise databases anymore, and they just reu-used credentials and scrape the data from these accounts, and then they call that a data leak. Think about that. When security headlines are made without even any real security issue being exploited. I think that’s the best example that security is getting better. So maybe cynically speaking, maybe we have to invent security issues to keep our jobs. And so recently I thought about the terms “cybersecurity” and “hacking”. And I came to this conclusion that cybersecurity describes the whole package. Of course a denial of service is bad for a business. With this video I was not trying to say a DoS issue is not an issue. It is an issue. BUT I did want to explain why for me these issues are boring. They are not satisfying, because they are unfixable. For high reliability and critical infrastructure it is an important topic. But you know who deals with that? Not security researchers . Site reliability engineers and sysadmins. The job to “defend against Denial of Services” for example, is the work of implementing failsafe processes, technical solutions to be notified when something goes down, being able to on the fly divert malicious traffic, have backup instances ready to go - it’s much more active work than we as hackers like to think. It requires dedicated staff and monitoring. You solve the denial of service and availability issues when they happen. And so I think for most businesses it’s nothing you need to worry too much about. Honestly, ignore it and deal with it when it becomes an issue. When you actually have somebody attacking you. Then you can start the whackamole game with that attacker. But I don’t think you need to start the whackamole game with bugunters already. So when I mean ignore the issue, I don’t mean you not care about the issue. You have to are about the issue. It’s basically blue team work you have to Implement internal processes to deal with when it happens. I’m just saying there doesn’t exist a magical fix you can figure out through a bug bounty report. And I just realized for myself, what exactly is interesting to me. I think vulnerabilities and bugs that can actually be fixed, they are a lot more interesting. And that work has direct impact. Because a fixed bug is fixed.
