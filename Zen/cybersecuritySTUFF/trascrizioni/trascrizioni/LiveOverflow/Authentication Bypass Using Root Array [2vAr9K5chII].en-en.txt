After this I’m still confused. Based on what I know about hacking, and having read source code of probably hundreds of websites, It makes no sense to me to test for this. So I decided to write to Eslam, the author of this article. “I saw your article about the auth bypass. This is so weird, I’m really curious how you found this. Why did you test for this?” And he immediately offered to do a live demo. I sent him a google meet link and he told me why he tested this weird root JSON… Turns out… it was an accident. He explained that he wanted to see if the site supports XML requests, so he used the burp Content Type converted, and converted the request to an XML request. This makes sense, because if that works you can also test for XML related issues like XXE. But the request didn’t work. And here now comes the crucial part. He then wanted to change back the request to JSON, used the same extension, content type converter, convert to JSON. And the extension turned this XML data into this JSON. The converter saw the password and email within a root element, so it created a root object, and put password and email inside. Oh man. The whole time I thought “root” had the meaning of admin or something. Root access. But it was a remnant of the XML request body. Look at my reaction from the call at the moment where he showed me that “So I tried to use the same extension to convert back to json, and this added root by default.” Finally I had the answer to why he tested for this. It was just an accident. After he saw how important that detail was for me, he updated the article to include these steps as well. Explaining that he used the extension. Finally we all have an answer to why he tested for this. I think this is important because the reasoning behind WHY we test for specific things are as important as the test themselves. So turns out this is not some crazy weird obscure implementation that he figured out to hack, it was a happy little accident. I can live with that. Actually I can’t. My curiosity obviously just increased. I wanted to understand why this worked. What is the root cause and can we actually learn something from this? So pay attention. I think now it gets interesting. After the call with Eslam, he thought about it a bit more and added to the article, a theory of what might have happened in the backend: Maybe “The target uses a custom framework, and also a custom function that deals with the login process”. He also wrote up a bit of example logic with a custom login validation. How it maybe could look like. This of course is just a theory. A coding theory. But I think this is wrong, and I think can do better. In the article screenshots he censored the cookie name. But thanks to the private showcase by Eslam I was able to figure out more. Because I know, the session cookie name is actually “ci_session”. And a simple google search reveals that this is the name for session cookies in Codeigniter. So now we know that the website is written in PHP using the Codeigniter framework. Big websites and services like google, twitter, facebook, they run on mostly custom code, very complex logics. Which means weird stuff might be implemented there. But generally for “basic websites” like this target, I doubt there is anything really custom. It’s too much work, especially when you already use a framework to handle a lot of it for you. And they use the popular PHP framework Codeigniter to implement their site. So I believe the answer to what happened here, lies in the way the framework is used. Or more precisely a mistake developers could make when using the framework. So how do we figure that out? Well, usually authentication is implemented using a database. In PHP it’s common to use SQL stuff. So I wanted to see how you do SQL queries in codeigniter. I dug a bit into the codeigniter documentation and looked at a few other example codes I found using github, and that’s when I learned about the query builder. Now I need a test setup to play around with this. using a docker image and docker-compose file I found somewhere, I setup a basic example and copied stuff I needed from other random projects. Getting examples setup like this is super annoying, but eventually I had one where I can build SQL queries and even accept JSON requests. So here is a controller that takes a JSON request, prepares the WHERE clause, and passes it to the query builder with getWhere. As you can see, if we have wrong credentials we get notfound. But the code checks for if user and password even exist. If not, where is empty. So if we pass in any other json, it will actually succeed. We simply select the first user we find in the table. And it turns out, this JSON request in my test, also worked on the target from Eslam. So I told him my results: “if the where clause is empty it matches everything and returns the first row”. and {"asd":"lol"} also returns one user. Because it's missing username and password. $where is empty, thus returning a row. And this is what I believe the code looks like on the backend. The programmers probably made a mistake with maybe some error checking code, checking whether username and password is properly set, and by passing in JSON data like this, the where query ended up being empty. This is super logical to me and I can totally see how this code can happen. Which means, the title of Eslam’s article is completely wrong and confusing. The Authentication bypass didn’t happen because of using root array. I knew from the start, this made no sense. I’m proud of my tingly feelers knowing that. Anyway, after I showed him my results that basically empty JSON works as well, he updated the article once again. Extending the title with “empty array”. Which is already better. But he even improved it even further on his personal blog. Where the title is “Authentication bypass using empty parameters. And now I think we reached a pretty correct title. Also in there he added that an empty JSON payload worked as well. But I think now that we know even more about it, it could be further improved. “Authentication bypassing in CodeIgniter due to empty Where Clause”. And then I’d explain that by removing username and password from the query, it caused the backend not to create a where clause, leading to an authentication bypass. This could be a somewhat common issue for websites developed with codeigniter, so pay attention to that. And NOW we have a really valuable writeup because we now help pentesters in the future to understand that this could happen. And they can test for it. Cool! But I have one more treat for you. This authentication bypass was not his only finding. Eslam didn’t publicly list all the other issues they found on this client. But they showed me during our call. Turns out, they also found a somewhat weird SQL Injection issues. And by having seen one of those example SQL injection requests, I think I managed to identify another potential programming mistake in CodeIgniter. Remember how we built this where clause from the JSON request? As a programmer you might think you are super clever by simply passing the whole JSON request into the where clause. If we have a request like this, then the PHP array would look the same as if we assembled it by hand. Makes sense, right? So when you have minimal beautiful and working code like this, the login still works. Try wrong credentials, you get “not found”, try correct credentials we login. BUT! See what happens if we modify one of the values here. Mh nothing happens. That is good, because of course CodeIgniter being a framework should take care of user controlled input so it doesn’t lead to SQL injection. BUT change the key here. You have an error in your SQL syntax. Turns out, if an attacker controls this part of the where clause, in this case we control it because we just take the complete data from json. We get SQL injection. And this looked exactly like the SQL injections they found on this original target. Of course this is not a common mistake, not every developer makes that mistake, but here on this site it happened. I’m pretty sure they wrote code similar to this. And if it happened here, I’m sure it can happen again. So we figured out a second potential issue for codigniter apps. Accidental empty where clauses, or straight up SQL injection. I’m really curious though, does anybody of you know this already? Is this something that is documented somewhere? At least in the official documentation they don’t seem to warn about it. They only warn about RawSQL. And even for the builder “where()” feature they explicitly state “All values passed to this method are escaped automatically”. Which I guess is technically correct. The values are escaped, just not the keys. Mh! Anyway, if you know more about it, let me know. And if this is indeed something not really documented, then cool!
