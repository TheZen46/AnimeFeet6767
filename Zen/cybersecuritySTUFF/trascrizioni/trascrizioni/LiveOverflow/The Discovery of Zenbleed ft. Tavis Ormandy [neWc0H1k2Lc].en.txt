Well… think about big datacenters and servers you can rent, like compute instances from Google Cloud. “Because of cloud computing, multiple users can share the same resources. So making sure it’s safe to share a CPU between multiple untrusted users is very important.” And because it’s this important for Google, they actually created a new CPU security research team and Tavis Ormandy is part of it. “So after 10 years of being on Project Zero, Eduardo told me about this new team for studying hardware security at google. And that sounded very exciting and I thought, yeah why not, let’s do it!” In case you don’t know, Tavis Ormandy is a very well known and skilled security researcher with a huge track record. Let me just quote here from wikipedia: Ormandy is credited with discovering severe vulnerabilities in LibTIFF, Sophos' antivirus software, Microsoft Windows, [...], FireEye products, glibc … and do you remember the really cool cloudbleed vulnerability? A buffer overflow in cloudflare leaking HTTP request data from other people? Yeah. Tavis is incredible, but the REASON why I wanted to mention this, is because you might notice a pattern here. Yes he found vulnerabilities in tons of DIFFERENT software. So what’s the pattern? Well.. it’s all software. So how did a software guy find a “hardware” vulnerability? “I feel like as a software vulnerability guy, I feel like I’m bringing fresh set of eyes onto this that maybe people who are very focused on CPU security haven’t used before. Because the people who have worked on this stuff are more EE focused. So I feel like I’m bringing a new perspective” And this perspective he is talking about is his experience with fuzzing. He has a lot of experience fuzzing various software. “We were experimenting with new ways of fuzzing CPUs. basically we wanted to apply the same kind of fuzzing methodologies we used for software, we wanted to apply that to hardware. And so if you are trying to fuzz software, the best performing fuzzers always use feedback. They get feedback from the software being fuzzed. And that’s usually in the form of code coverage. So when you discover a new interesting piece of code, the fuzzer knows about it, and knows to keep testing this area. Or not throw away this testcase. Or use it as an input for future fuzzing. So let’s talk about this. To implement a “modern” fuzzer you need basically 3 components. First, you need something to generate random input. By the way, I have created a very detailed series about fuzzing the sudo program to rediscover the sudoedit vulnerability. So let me use sudo as an example to explain those components. For sudo we want to generate random program arguments. So we want valid arguments like -h, -v or -s. But also random strings. Like AAAA\ or abcd1234. Pretty simple. Then you need a component to detect if the generated input leads to a vulnerability. For sudo, being a C program, we probably are looking for segfaults. Segmentation faults, so the program crashes. These crashes are generally a good indication that we found an exploitable bug and crashes are easy to detect. And lastly we want coverage information. We were using afl to fuzz sudo, and afl basically inserts additional code into the sudo code, which is used to collect information about the executed functions. And the trick is now, this coverage information can be used as feedback to the input generator to mutate the input trying to keep increasing the coverage. We want to reach as many functions in sudo as possible. And yeah, for fuzzing software these components make sense. But how do you implement these components for fuzzing CPUs? Generating input is pretty straight forward. You just need to generate random assembly instructions. But the other two components, detecting whether something interesting happened(?), and the coverage information(?), I have no idea how you could implement that for CPUs. And that’s where me and Tavis differ. He, of course, had a brilliant idea. “There is no coverage for CPUs. So when you are fuzzing them, basically what people mostly do is just generate a random stream of bytes, execute it, and see if anything interesting happened. But that is super hard to do. And so what we wanted to do was, instead of code coverage we would use performance counters. So that when something interesting happened, when some interesting event happened. The fuzzer would monitor that, notice that something is interesting and count that as some interesting sample that needs to be integrated into the set of samples we are fuzzing. Okay. So Tavis said they are using performance counters to measure “coverage”. But I didn’t understand that right away. I imagined a “performance counter” to be basically an instruction that tells you how much time, or how many cycles have passed. Counting how many instructions the CPU executed or so. Well.. that is kinda true. But performance counters are so much more. “So what we do is, we measure the performance counters of the entire systems before and after execution. And there are performance counters for all kinds of interesting architecture states. If you look at the list of documented performance counters, there are thinks like whether any microcode assists were used, whether there were any stalls caused for any reasons. After that we can say, whether the cpu was doing something interesting while executing this. And we don’t know what it was. But it doesn’t matter. The point was, that something interesting happened.” “Ahh yeah okay. In my mind the performance counter I only had like cycles counter in my mind. But I didn’t realize that there are performance counters for all kinds of other metrics.“ “Oh there are tens of thousands of them. And most of them undocumented. Some of them are documented and they are so interesting to read through. Some of them use terms I’m just not familiar with” “Oh wow. There are so many” “I think there was some like frontend retired latency &gt;= 2, bubbles &gt;=3, and it turns out that this one was like another good one. I don’t know what that means, I just know that there were these magic numbers and I wanted those numbers to go higher.” performance counters or hardware counters are a set of special-purpose registers built into modern microprocessors to store the counts of hardware-related activities within computer systems. Advanced users often rely on those counters to conduct low-level performance analysis or tuning. Here is a list of documented performance counters for intel CPUs, and there you can find metrics of how many CPU cycles were executed. Like I assumed. But I also Imagined there to be a SINGLE metric for that. BUT look at this, you have the amount of clock cycles when the thread is unhalted and clock cycles when at least one threat is unhalted - so even for something simple like counting clock cycles there are many variations. And so there are lots of different counters like that. Counting how many transitions between ring 1,2 or 3 to ring 0 happened. Just scroll through that list. It's insane. Here is also the bubble one Tavis mentioned, which counts the “Retired instructions that are fetched after an interval where the front-end had at least 3 bubble-slots for a period of 2 cycles which was not interrupted by a back-end stall.”... like Tavis, I also have no clue what that means. But this is the secret to the fuzzer. This is his coverage information. While you cannot instrument and trace the hardware internals of the CPU, the performance counters tell you basically what happened. There is a counter that goes up when a branch was mispredicted by the speculative execution. Or counters that count the amount of cache misses. So these performance counters can tell you whether a certain CPU feature was used, very similar to how afl instruments a binary to tell you whether a certain function got executed. What a clever idea. And when I understood that, I immediately realized something. “Because there are so many, and you don’t know which ones are the interesting ones. The fuzzer performance could greatly be impacted by which of these performance counters you decide to use for the fuzzer.” “So yeah, a lot of the work was figuring out which counters are useless, and which ones seem to, just as a heuristic to make more interesting code.” So coming back to the fuzzer components. Now we understand TWO of them. We can generate random instructions, and we have feedback. When we generate instructions and observe that they make certain performance counters to go up, our instruction generator can favor those generated instructions and intelligently evolve and mutate those inputs. This genetic algorithm then automagically creates more and more interesting instruction sequences making more interesting performance counters to go up. Cool! Now the only last puzzle piece missing is, how do we even detect a CPU bug. In C programs we often look for segfaults, or crashes. In a Java program we maybe would look for exceptions. But how can we detect when something interesting in a CPU happens? To figure that out, we could look at known CPU vulnerabilities and see how they worked. What do they have in common? Is there a pattern that we can test for? And it turns out, yeah. They all have something in common. Be it foreshadow, RIDL, meltdown, specter, retbleed. All of them are side-channel, or covert-channel attacks. A while ago I actually made a video about RIDL, a CPU vulnerability in Intel CPUs, and that video kinda complements this video here. Because in that video I explain in a bit more detail how these side-channel leaks worked. And I also explain speculative execution. So if you don’t understand either, please checkout that video. Anyway. Basically, in those known CPU vulnerabilities, you always have these instructions to trigger the vulnerability, they generally involve speculative execution that loads something in a cache, and then afterwards you measure cache access timings. Which means, if we are fuzzing this part, we can use the same cache measurement to detect a leak. At least ALMOST. Just a small problem? If we measure a short cache access time. How do we know it’s a leak and not just the code having loaded the cache totally legit before? Well… Tavis had a second brilliant idea. “For fuzzing software, a crash is easy to recognize. Some signal you catch and then you can act on it. But like with a CPU bug that just leaks a bit, how do you even realize if a bit was leaked.” “Oh yeah, so that is a really interesting problem. We came up with a new solution for this. And we call it “oracle serialization”. So what you do is, you generate a fuzzed sample, and then you transform that by adding serialization instructions between every instructions. What serializastion instructions do is to reset every internal state. The internal instruction parallelism. And that’s things like out of order execution and things like that. So then you have two samples. You have one sample that will just run and record state before and after. And then you have that serialized oracle that should produce the exactly same output, but it doesn’t use any instruction parallelism. Basically you have the serialized example. The idea is the output should be identical, but if iran’t then you know you went wrong somewhere.” “That is so clever! The light just turned on in my mind. Because I was wondering. If you instrument with afl a binary, then you insert instruction to gather the coverage. So I was wondering, ok if you now start inserting coverage, even just the performance counter to store that away somewhere, that already like messes with everything. But that is so clever to basically use, if I understand correctly, instructions in between, that kinda make sure everything is really serially executed. Like force these instructions to slowly execute. Don’t make anything fancy with those instructions. And compare that to the clean result and see if something came out. Wow that makes so much sense now that you say it.” “A lot of the bugs that people are finding are in speculation. And this bug included. And some of these serializing instructions are speculation boundaries like lfence. After every single instructions we reset speculation as well. So we know for sure no speculation can possibly be happening, because every instructions is followed by a boundary.” “Ahhh that is so clever. That makes so much sense. I love it when solutions seem so obvious after you hear them, but I know I would have not thought of that.” And with that, we have the final component for the CPU fuzzer. We can now generate random instructions, use performance counters as coverage information, and detect leaks by comparing the result of the test case with the execution of an oracle, which uses additional instructions to basically “disable” all kinds of fancy CPU features. Awesome… Now we understand how Tavis and the team were able to fuzz CPUs. And with that let’s run the fuzzer, and learn about the moment that Tavis found the issue. Let’s talk about zenbleed. “Tell me about the moment when you saw that sample, what went through your mind. And did you also have false-positives? How did you identify that this is actually in this case an issue?” “Yeah so it’s still very new in development. And the way we were developing it. We would get it to run, and then usually after a few days or few hours it would find a sample that didn’;t work correctly. And usually this was a bug on our end. It’s a sequence of instructions we werent transforming into a serialized form correctly, or we were not handling some side-effect we didn’t expect. Everytime we find an error we would just fix it and start again. And so this time the result just didn’t make any sense. And we just couldn’t figure it out. The state seemed to be coming from somewhere else on the machine and we just couldn’t control and couldn’t explain where it came from. And so it took a while to minimze it. And figure out exactly what was going on. And as soon as we saw it we realized it, this is state from the other core. So that’s a bug. That can’t happen.” “But this was like this typical process when you start fuzzing a new target. You go into this iteration loop where you start instrumenting it. And you realize you missinstrumented it and its crashing because of your instrumentation and not actually a bug. So you were still in this development process. And so you stumbled over a behavior, that you maybe even assumed it probably was just a mistake on our side, and you were not even expecting to find something.” “Yeah I mean this had happened so many times. We were a few weeks in development. And everyday I had a few crashes to go through. Figure out what went wrong. And fix serialization. And I had no reason that was another case that wasn’t another case exactly the same problem. But this time it was.” So here is the unminimized sample that lead to a different state when comparing the oracle (the slow sequential execution), vs. when it was executed with all the speculative execution and parallelism features of the CPU. It took them a while to minimize the finding and identify which instructions triggered the state difference. But eventually they came up with this. They discovered zenbleed.
