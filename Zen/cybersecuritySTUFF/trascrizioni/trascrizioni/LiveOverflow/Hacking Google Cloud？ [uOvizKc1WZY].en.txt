TBD Title: Hacking into Google Cloud Since 2019 Google celebrates, every year, the best hackers who hacked into … google cloud. Yeah… Google gives out prizes for the best security issue found in their own Google Cloud products. And it’s time again. The winners of the GCP Prize 2022 are in. And we can now look at the best writeups to learn how WE could have hacked into Google Cloud. This is especially interesting to me, because our learning platform hextree.io, specifically the lab system where you can launch challenges to practice hacking, we are running on Google Cloud. So I want to know if any of those security issues could have affected us. Besides that, I’m also working as a security professional and I try to find issues like those all the time - so for me this is also a moment of reflection, to ask myself “could I have found these issues myself?”. But I really hope I can answer this with “no”. Because… the GCP Prize for the best bug, is 133,337$. And that is a crazy amount of money. And if I realize I could have found these issues myself, then urgh… Every year I tell myself I should try to find a bug. But then I don’t try. And every year since 2019 I regret that I didn’t do it. So let’s see this year. Will I regret not having participated? We will see… Let’s start with the 7th place and work our way up. &lt;intro&gt; Command injection in Cloud Shell, by Bugra Eskici, this got 7th prize and got awarded an additional 13,337$. Cloud Shell is a feature where you get a basic shell in your browser to access various Google cloud things, and it also comes with this integrated IDE. And this is interesting because in 2019 there were cloud shell bugs winning the gcp prize and then in 2021 there was another one, even with the same title like this one in 2022. a “Command Injection in Google Cloud Shell”! But it’s also not that surprising. Looking back at the URL of the cloud shell back then, it is very different to the one today. Which shows that this feature is constantly in development and changing - and changes increase the chance of new bugs. So here we see the result. Anyway, Bugra found out that the project name GET parameter appears to be placed inside a python CONFIG script. And this script is executed. See here the Syntax Error when using a single quote in the project name. And now it’s pretty straight forward. Inject some malicious python code and if a victim opens this link, you get arbitrary code execution in their shell. “Will I regret not having participated? We will see…” Let’s not think about it, and just be happy for bugra. Congrats. I also really really like this bug because of how straight forward it is, and also easy to understand writeup. Good job. Now let’s move on. Prize number 6. $13,373 goes to Obmi. That is a familiar name! Obmi also won a prize in 2019! He actually got this year's prize for the writeup of three bugs. First one is actually a XSS in Cloud shell. It’s basically a reflected XSS with the file name of the uploaded file. See here in the screenshot, the name. This is really interesting because this is similar to the reflected XSS obmi found in 2019. Look at this. Here it was on the error page, but it was also file related! “File not found”! Fascinating. But this is not all. To realistically trigger this XSS you need to combine it with a CSRF, or it is just a self-XSS. And so the CSRF is actually the second issue described here. Now you can combine the CSRF and the XSS into a single exploit. Here is the javascript code of it. First it dynamically creates a file upload form with the XSS payload in the file path. And then submits the form. Sounds simple, but there is a small detail that makes it a little bit tricky. Because the host that is vulnerable to the CSRF and XSS has a random ID. And as an attacker you would need to know this. In OBMIs writeup of 2019 he actually described a method to leak the hostname through a redirect and triggering a CSP report rule. So how did he do it this year? Well, the writeup is not mentioning it directly. But if you watch the proof of concept video you see a weird interaction. There is a small window popping up and instructions to drag and drop the image. And I’m not 100% sure, but I think obmi found an endpoint that redirects the unique ID with a specific image. And when you drag and drop an image, you can write some javascript to capture the URL of the dropped image. So if this image is indeed hosted on the unique URL, then this drag and drop will leak the unique host ID. It’s just a guess, but I’m like 70% sure that this is what happens. So the full attack requires some user interaction, but still a cool technique. But this was not all, there is a third issue, a XSS in the markdown viewer. Also pretty interesting because there was CSP to prevent javascript execution, but with a meta tag you can redirect the embedded frame to your target domain, and turns out the parent frame had an insecure postMessage handler that can be used to XSS the parent. But this is still not all, because lastly Obmi showcased a cool post-exploitation technique that I did not know of. Apparently there exists a NEL response header, which stands for “Network Error Logging”. And when your server returns the NEL header, then any network request errors are forwarded to the specified report_to domain. So that’s kinda similar to the CSP report uri, just for network errors. And in this unique app context that is cloud shell, Obmi explained that you can replace the webserver running on your current cloud shell with a server that sets this header. If then a user loads this server, the browser then sees the NEL header and remembers, that any networking errors should be reported to that attacker controlled server. And that is kinda like a backdoor, because “Every time, when user starts a new devshell session, the browser sends authorization requests to the VM origin with the oauth token in the url. And because the devshell is slow and has not started yet, the server responds with 503 http error code. That is a network error, so the browser will send a report” to the attacker controlled server. Leaking the oauth token. Very clever. Didn’t know about this technique. And I guess Google agreed and so OBMI wins the 6th GCP Prize. Now we come to the top 5. Here we have a whitepaper with the title Kubernetes Privilege Escalation: Excessive Permissions in Popular Platforms, by Yuval Avrahami and Shaul Ben Hai from paloalto networks and they won $17,311. So this is not even a typical bug report, it is a research paper covering more than just google cloud’s kubernetes products. This paper talks about how kubernetes DaemonSets often run with excessive permissions. And this is common in lots of different kubernetes setups. I’m still learning a lot about kubernetes, and for me I actually learned from this what demonSets are. So let me now explain what I just learned to you, demonsets are basically just pods (or containers) that run on every single node, so every single machine of a kubernetes cluster. And demonsets are often used for very specific machine configurations and thus often have higher privileges. So if an attacker exploits one pod, for example a webserver, and manages to escape the container, to the host. Then the attacker can access the privileged demonset container and can then use the priviledges, as what they call a demonset trampoline, to then compromise the complete cluster. And here GKE, Google Kubernetes Engine, when using Dataplane v2, was also using excessive permissions. After this was reported, Google fixed it and even gave them a 13.000$ bounty for this. Also besides this paper, they released a tool that you can use to check the permissions in your cluster. So while this whitepaper does not directly describe a typical bug or security issue, it’s really defense in depth, overall this research contributed to more resilient kubernetes setups in general. Also Yuval presented their research on “trampoline pods” at KubeCon. So if you are interested in more details, I will link the talk below as well. So as you can see, this research really helps not only Google but the whole kubernetes ecosystem can learn from it, and, I guess, because of that, Google wanted to reward this with the 5th GCP prize. Next we have something special. a Triple Kill. The bug hunters Sivanesh Ashok and Sreeram KL teamed up and won 4th, 3rd and 2nd prize. $31,311 for Client-Side SSRF to Google Cloud Project Takeover, another $31,337 for Bypassing Authorization in Cloud Workstations and then $73,331 SSH Key Injection on Google Compute Engine. Damn… what bloodbath. So let’s see what they found. The SSRF to Google Cloud Project Takeover is pretty straight forward, they found an endpoint called proxy, which contained a domain. And the response looked like it contained authenticated data. This definitely screams SSRF. So they tried to set their attacker domain, but that didn’t work, there was a check. However the check appears to be implemented with something like url.contains(“compute.googleapis.com”), because attacker.com/compute.googleapis.com actually worked. And when tricking a victim to visit this URL, then google would send a request to the attacker domain with the google compute credentials of the user. Which can then be used to basically takeover the google cloud project. Pretty cool. Also the writeup discusses a bypass they found after the first fix to properly restrict the domain to google.com, because they managed to find an open redirect on feedproxy.google.com. Pretty cool writeup. But let’s move on to the next one. Bypassing Authorization in Cloud Workstations, and this turns out to be basically an oauth vulnerability. Cloudworkstations are kinda similar to the cloud shell we have seen before, but it’s intended as an actual workstation. And as they write here “Using a non-google.com subdomain means the workstation cannot access a user's google.com cookies. So it should use another means of authorization.“. so they looked into the oauth authentication flow and noticed that the redirect parameter contained a state object. And this state object contained the actual redirect target host. So by setting the target host to their own domain, they can craft an oauth link, that when visited by a victim causes the workstation JWT, the authentication token, to be sent to the attacker host. Cool. Kinda typical oauth vulnerability, abusing the redirect and not properly implement the state parameter. you would kinda think Google knows how to implement OAuth by now. But this is a typical flaw of mine. I often assume “they should know this” so it’s not worth my time to check it. And I would probably have not found this issue because of that. And yet this example shows, it can still happen. You can never be 100% sure without actually checking. And I guess this Oauth issue was a surprise to Google as well, because they rewarded this writeup with the 3rd GCP Prize. And now let’s come to the last issue of the three. The one that got them the 2nd GCP Prize. This gave them an additional $73,331. SSH Key Injection on GCE. This issue affected the ssh-in-browser feature of Google Compute Engine. This feature looks similar to the Cloud Shell that we have seen before, but this specifically is a ssh shell into an actual running compute engine instance that you rented. And here the hunters noticed a feature where you can enter the username, and it will then use this user for the shell. So I think the expected usage here is that on this machine there exist different users and you can choose which user you want to use. But that’s not only what it does, as the hunters have figured out. So first they noticed that this endpoint was vulnerable to CSRF - just make a victim visit a URL with the GET parameter newLinuxUsername and surprisingly, the linux username will be added if it didn’t exist before. Kinda annoying, maybe disruptive, but not really a serious security issue. BUT then they also noticed, after playing with different special characters in the username, that for each new username, a ssh key is added. And look at what happened when they tried a command injection payload with curl. The key format is completely messed up! And it looks like they can control both the username AND the key part. Which means they can craft a special injection payload to inject their own SSH key into the authorized_key file. You can see this here in the proof of concept video. Open that crafted URL, wait a moment, and they can ssh into the server. Wow… “Will I regret not having participated? We will see…” Anyway. I was wondering why this functionality exists, I mean a feature to select which user to login as is fine, but why write a SSH key to the authorized_key file? And Google told me that the reason is simple. The javascript frontend code actually generates a random ssh key that is then submitted to the machine via a backend API, so that the browser SSH client can login with that key. Also this feature is useful to fix your machine, in case you accidentally delete your user’s home folder. In such a case the authroized_keys file would be missing and you couldn’t login via ssh anymore. So this functionality would also write a new SSH key, so you can still use this browser ssh feature to login. So this feature is useful, but unfortunately this was not implemented properly, and it was vulnerable to this ssh key injection. Nice. And now… the moment we all have been waiting for. Who won the GCP Prize 2022? What was the best security bug in Google Cloud? Drumroll. Drrrrrr. Privilege escalations in GKE Autopilot, by Yuval Avrahami, so Google Kubernetes Engine again. “In June 2021, Unit 42 researchers [from paloalto networks] disclosed several vulnerabilities and attack techniques in GKE Autopilot to Google.”. Sounds scary, and we at hextree.io also use GKE Autopilot. BUT there is one strong requirement for this to work. The attacker needs to be able to create pods. So maybe a compromised developer account or so. But if that is the case, then the attacker “could have abused these [issues] to escape their pod and compromise the underlying node, escalate privileges and become full cluster administrators, and covertly persist administrative access through backdoors that are completely invisible to cluster operators.” And in case you didn’t notice, we know Yuval from Paloalto networks already, because they got the 5th prize this year for their whitepaper on excessive demonset permissions. And remember, that whitepaper described a situation where you already have a pod escape, taking over a node. And then you could abuse the privileged demonsets. Well, this writeup now, of the first prize, explains how a user that can create pods can escape to the node, and then they could make use of the demonset research. That’s kind of a cool follow-up connected story. Anyway! let’s have a closer look at their findings. they found issues in Google Kubernetes Engine Autopilot. So it’s especially interesting for me. And we already know, the attacker in this case needs to be able to create pods. But if that is given, how does the pod escape work? Well… standard pods usually don’t need special privileges. So Google prevents you from running high privileged pods. However, there are a few use-cases where you maybe need to give a pod special privileges. And for that purpose, Google has an allowlist, that restricts what is allowed to run with specific higher privileges. They looked at this allowlist and they found this datadog image that has an exception allowing mounting different host paths. Most interesting is of course the containerd socket file, that’s like docker.socket, and basically it can be used to run any privileged containers you want. But just running this image does not necessarily help you, because you don’t actually want to run this image as intended. How can you execute arbitrary code so that you can access containerd? turns out you can specify an alternative command to execute, and they simply execute bash. So they now get a shell in a privileged container that can access the containerd socket. Which can be used to create another container with full host filesystem access. Achieving a pod escape, compromising the complete node. Cool! But this is not all. They then went further to assess the impact of the node compromise. What can they actually do with it. And eventually they also managed to escalate privileges to a complete cluster takeover. And in this process they also developed a tool called sa-hunter, which they used to assess excessive permissions. WHICH is the predecessor of rbac-police, which is the tool they mentioned in the other whitepaper. Anyway. The privilege escalation was not all they did. They even figured out an interesting way to backdoor the cluster. If you are interested in that, make sure to read the original writeup. So they documented lots of different things. And in the end also looked at the bigger picture beyond google’s kubernetes setup, “Preventing Similar Attacks on Kubernetes Environments”. And so this is probably the main reason why they won this years GCP Prize. This writeup is not about a especially critical bad vulnerability - the requirements here are that you already have permissions to create pods, so that shouldn’t affect too many customers using Google’s Kubernetes Engine. BUT the researcher really dug deep into the topic and highlighted lots of other weaknesses in Google’s setup, “this research led to several hardening improvements in Autopilot that make it a better secure-by-default Kubernetes offering”, so it obviously helped google, but it also benefited lots of other kubernetes environments. Also here is a writeup from Google on their security blog “Privileged pod escalations in Kubernetes and GKE”. Basically discussing the direct results of the research by Yuval - so this is the 5th prize and also the 1st prize. And I think the fact that Google even wrote this blog post about their changes, shows the impact this winners report had for Google Cloud. So Congratulations Yuval for winning.
